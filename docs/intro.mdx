# Creating a Module Data + Texture Pack

## Description

**Truly Modular** introduces many unique concepts and terms.  The most important of these are **Modules** and **Module Properties**.---### Modules / Module Instances- A **Module** refers to the base, blank definition loaded from data.- A **Module Instance** is the actual application of a module on an item.Module Instances exist in the context of the item they're applied to, along with other modules. They follow a **tree structure**:- There can only be **one root Module Instance**.- Any module can have **multiple sub-modules**.---### PropertiesAll item behaviors—such as name, durability, rendering, and more—are controlled through **properties**.  A module, at its core, is simply a **list of properties**.This list can be further modified by:- **Materials**- **Synergies**- **Skins**- or other property resolversHowever, item properties are **static** with respect to the module structure.  That means an item **cannot dynamically change its properties** based on external context (e.g., who is holding it or which dimension it’s in).  This limitation exists because such context isn’t always reliably available.> 💡 **Note for Java developers**:  If needed, you can write custom logic to conditionally modify the module resolution based on context.  However, doing so places full responsibility on you to **validate and manage those conditions** correctly.
